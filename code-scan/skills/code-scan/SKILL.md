# Code Scan

## 何时使用

- 用户要求"扫描整个仓库/多个仓库""找死代码""找重复代码""哪里性能有问题""做一次代码质量审计"
- 不适用于:单 PR 审查(用 GitHub 审查 bot)、只看改动(用 `git diff` 流程)

## 方法(Devin 式:全局查询先行)

1. **准备**:仓库通过 `git clone --depth 1` 取到 `.code-scan/repos/<name>`;失败记录进 notCovered,不中断整次运行
2. **Plan(全库规则)**:每个仓库一个规划员,产出作用于全库的确定性 `selectors`:
   - `glob`:路径规则(如 `src/**/*.ts`)
   - `grep`:模式查询(如未使用导出候选、危险模式)
   - `tool`:工具规则(knip/jscpd/madge)
   同时产出精简仓库地图(模块树/职责/入口/依赖边)
3. **全局执行**:脚本用 `files.glob`/`files.grep` 在整库执行 selectors;工具执行员在仓库内跑 knip/jscpd/madge,候选并入命中集
4. **Shard(命中项分片)**:命中项按路径排序、按文件数切批(默认每批 ≤8 个文件、每仓库 ≤4 批)——**分片的是命中项,不是全量文件**
5. **Map**:每批一个独立审查员,复核命中项是否真问题,可整库 Grep 补充上下文;最多补 3 条命中外发现
6. **Confirm**:每条发现交给独立复核员复现;未能复现标 `unconfirmed`,不删除
7. **Reduce + 全局审查**:评审长去重排序;全局评审员找跨批次模式(重复/不一致/分层违规),最多新增 5 条,同样要复核

## 维度与证据要求

| 维度 | 查什么 | 证据门槛 |
|---|---|---|
| 质量 `quality` | 可读性、边界处理、错误处理、一致性 | 引用具体文件行,说明为什么是问题 |
| 冗余 `dead-code` | 死代码、重复实现、未使用导出 | 优先工具(knip/jscpd);工具缺失只做代码阅读并在 notCovered 说明 |
| 性能 `perf` | 算法复杂度、N+1、重复 I/O、无谓分配 | **必须给复杂度论证或基准数据**,空口建议不报 |

## 严重度

- `high`:数据丢失、崩溃、错误结果
- `medium`:明显缺陷、显著性能退化、维护成本高
- `low`:风格、小优化

## 输出

- `WorkflowReport`:`conclusion` / `findings`(含 `status`)/ `verified` / `notCovered`
- 运行中实时更新发现看板(`report`),结束后发布 markdown 报告(primary artifact)
- `unconfirmed` 不等于假阳性:复核员未能复现,但值得人工看一眼

## 模型选择

- 用户指定模型时,由命令解析 `ListModels` 后作为 `subagent_model` 传入,整次扫描所有子 agent统一使用
- 未指定则用会话默认模型;脚本内不写死模型

## 成本与安全

- 每仓库:规划员 1 + 工具执行员 1;每批次:审查员 1;每发现:复核员 1;另加评审长/全局评审员各 1
- **批次数按命中文件规模自动生成**(每批 8 个文件),默认不设总批上限;并发上限用 `max_concurrency` 控制(建议 4)
- 选择器单次命中上限 2000,超出记录进 notCovered
- 全程只读:审查员与复核员不编辑文件;扫描不开 PR
- 要修复用 `/code-scan-fix` 后续任务
