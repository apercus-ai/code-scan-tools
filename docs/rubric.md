# 扫描 Rubric

修改本文件后同步更新 `code-scan/skills/code-scan/SKILL.md` 与脚本 prompt 中的对应措辞。

## 选择规则(selectors)

规划员必须产出作用于**全库**的确定性规则，而不是文件清单:

| 类型 | 用途 | 示例 |
|---|---|---|
| `glob` | 圈定要审的代码范围 | `src/**/*.ts`、`packages/*/src/**/*.ts` |
| `grep` | 全局模式查询 | 未使用导出候选、循环依赖迹象、危险模式 |
| `tool` | 全库工具查询 | `knip`(死代码)、`jscpd`(重复)、`madge`(循环依赖) |

规则先在全库执行，命中项才进入批次复核——这样死代码、跨模块重复不需要靠分片运气。

## 维度

### 质量 `quality`

查：
- 可读性：命名、函数长度、嵌套深度、魔法数
- 边界处理：空值、越界、异常路径
- 一致性：与仓库现有模式冲突的写法
- 错误处理：吞异常、错误信息缺失

证据门槛：引用具体文件行，说明"为什么是问题"，不接受"看起来不好"。

### 冗余 `dead-code`

查：
- 死代码：不可达分支、未使用导出/函数/类型
- 重复实现：跨模块的近似逻辑
- 未使用依赖

证据门槛：优先用工具找候选：
- JS/TS：`npx knip`、`npx jscpd`
- Python：`vulture`、`radon`
- Rust：`cargo udeps`、`clippy`

工具不可用时只做代码阅读，并在 `notCovered` 说明"未运行工具"。

### 性能 `perf`

查：
- 算法复杂度（O(n²) 循环、嵌套遍历）
- N+1 查询、循环内 I/O
- 无谓分配/拷贝、重复序列化

证据门槛：**必须给复杂度论证或基准数据**。没有证据的性能建议不报。

## 严重度

| 级别 | 标准 |
|---|---|
| `high` | 数据丢失、崩溃、错误结果 |
| `medium` | 明显缺陷、显著性能退化、维护成本高 |
| `low` | 风格、小优化 |

## 复核规则

- 每条发现交给独立复核员（全新上下文），只凭证据复现
- 复现成功 → `verified`；失败 → `unconfirmed`（保留，不删除）
- 复核员不编辑文件

## 全局审查规则

全局评审员只做三件事，且新增发现 ≤5 条、必须带证据:
1. 同一逻辑在多处重复（跨批次）
2. 各批次对同一概念处理不一致
3. 分层/依赖违规（模块间不该有的依赖）
